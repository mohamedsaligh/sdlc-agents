# Decisions (ADR-style, newest at the bottom)

Short records of the choices that shape this repository, so future maintainers change them
deliberately rather than by accident. Add one entry per decision; never delete, mark `Superseded by`.

## D-01 · Manifests hold shape, not data
**Decision**: a manifest lists which tables, regions, events and keys a service uses; rows are fetched live via `__DEVCTL__`.
**Why**: data changes daily and per environment; shape changes with releases. Baking data in would make the map stale within days and force engineers to inject everything again.
**Consequence**: every data claim in an output must cite a `describe` file from that run.

## D-02 · Thin agents, thick map
**Decision**: agents route, load, reason and write; they do not try to understand the whole platform.
**Why**: 20+ services and 2,000 engineers cannot share a prompt that knows everything, but they can share a small, versioned map.
**Consequence**: reusability lives in `manifests/`, `schema/`, `templates/`; prompts stay short and generic.

## D-03 · Jira routing is a lookup, not an inference
**Decision**: BAs fill Market, Clearing, Product, Direction from a controlled vocabulary; the same strings are manifest tags.
**Why**: set intersection is deterministic and auditable; inference from prose is neither.
**Consequence**: a Jira without these fields is "not ready" and the agent says so at step 01.

## D-04 · Radius is confirmed by a real payment, not just by tags
**Decision**: step 02 traces one real baseline payment and reconciles the hop list with the tag-matched candidates.
**Why**: design docs drift; a production trace does not lie about which services ran.
**Consequence**: `trace` must be read-only and allowed against production (or a faithful UAT).

## D-05 · Four confidence lanes with explicit evidence rules
**Decision**: MAP 0.30, CODE 0.30, DATA 0.25, MODEL 0.15; deductions only with cited evidence; gate ≥70 overall and ≥50 per lane.
**Why**: a single number invites rubber-stamping; lanes show *where* the uncertainty is and what would remove it. Model self-assessment is weighted lowest because it is the least verifiable.
**Consequence**: tuning happens in `config/thresholds.yaml` and is recorded here.

## D-06 · Below the gate the agent asks, it does not plan
**Decision**: a failed gate produces `questions.md`, never an implementation plan.
**Why**: a confident-looking plan on weak evidence is the most expensive failure mode in a payment platform.

## D-07 · The Builder is deliberately dumb
**Decision**: it executes an approved plan literally, allows one mechanical fix per service, and stops on any second failure.
**Why**: trust comes from predictability. Intelligence belongs in the Solution Agent, where humans review before anything is built.
**Consequence**: plan quality is the lever; improve the Solution Agent and the map, not the Builder.

## D-08 · Approval binds to a plan hash and to git identities
**Decision**: `approval.json` records the SHA-256 of the plan (CR-insensitive); any later edit invalidates the approval. Each approver commits the file under their own identity; the Builder verifies `git log` authorship and refuses approvals authored by its own identity. CODEOWNERS + signed commits are the recommended repo controls.
**Why**: audit and infosec need to know exactly what was approved, by whom, and that it was what was built. A JSON file alone proves none of that.

## D-09 · One canonical agent file per agent; harness adapters are generated
**Decision**: `agents/*.md` is the source; `.github/agents/*.agent.md` and `.claude/agents/*.md` are generated by `scripts/sync-agents.py`.
**Why**: Copilot and Claude Code must behave identically; two hand-maintained copies would drift.

## D-10 · Every run is a folder, committed
**Decision**: `runs/<JIRA-KEY>/<EXECUTION_ID>/` with `run.json`, numbered steps, outputs, approval; raw tool responses are kept locally but git-ignored; normalized files are projected and masked by deterministic rules (contracts §C). Each agent commits its own run folder, never pushes. **Scale rule**: while one team pilots, runs live in this repo; before a second team or region joins, `runs/` moves to a separate `sdlc-runs` repository (same layout, `run.json.map_version` keeps the link) so the map repo's `main` changes only when the map changes.
**Why**: replayable, auditable, diff-able; the history of decisions lives next to the map version that produced them; 2,000 engineers cannot all commit into one repository's `main`.

## D-11 · Onboarding = one base pass + many slices
**Decision**: ONBOARDING runs a base pass producing `onboarding-context.md` (baseline, scaffolding list, work packages); each work package is then a normal run with `PARENT_EXECUTION_ID`.
**Why**: hundreds of epics cannot be one plan, and five engineers in three regions must not redo discovery.

## D-12 · Placeholders, replaced once
**Decision**: `__PLATFORM_NAME__`, `__DEVCTL__`, `__AI_PLATFORM__`, `__CODE_ROOT__`, `__DESIGN_DOCS_ROOT__` are the only environment-specific strings; `scripts/init-project.*` replaces them once.
**Why**: the repository must be shareable outside the firm's network without leaking names, and usable inside it without per-run substitution.

## D-13 · Design docs stay where they are, unmodified
**Decision**: design markdowns are referenced via `DESIGN_DOCS_ROOT`, never copied or restructured; a manifest stores the doc's SHA-256 and `check-drift.py` flags changes.
**Why**: the docs are reviewed assets with their own owners; the manifest is the machine-readable index on top.
